# asus-user-status-led — архитектура

[English version](ARCHITECTURE.md)

Подробный дизайн принятой системы: как устроено сквозное управление
светодиодом ASUS User-status, что уже проверено и почему отклонены
альтернативы. Это документ проектирования, а не дневник исследований —
здесь сохранены только сведения, определившие архитектуру.

Статус: дизайн принят, и v0 реализует его: CLI, демон,
пользовательский сервис systemd, правило udev и привязка Niri. Приёмка
на ASUS ExpertBook B5402CBA пройдена для ручных режимов, режима `auto`
(простой, захват микрофона, отсечение ложных срабатываний, реальный
звонок и семантика приглушения) и интеграции Fn+1, включая исправление
с фильтрацией событий по релевантности. Оставшийся объём приёмки:
визуальная оценка мерцания при перезапуске и жизненный цикл
перезагрузки/входа в систему. Текущее проверенное состояние — в
`CHECKPOINT.md`, стабильные правила проекта — в `AGENTS.md` (оба файла
на английском).

## 1. Назначение и границы

Этот репозиторий отвечает только за пользовательскую политику и интеграцию
для светодиода ASUS User-status:

- модель режимов (`auto` / `busy` / `off`) и её хранение;
- CLI для запроса и изменения выбранного режима;
- демон, вычисляющий режим и записывающий состояние светодиода;
- пользовательский сервис systemd, правило udev для прав записи и пример
  привязки Niri.

Поддержка ядра — внешнее предусловие: патч ядра разрабатывается отдельно и
не входит в этот репозиторий.

Проверенная аппаратная база:

- ASUS ExpertBook B5402CBA;
- ASUS WMI DEVID `0x00040019`;
- LED ABI: `/sys/class/leds/:status`;
- бинарная яркость `0`/`1` (`max_brightness = 1`).

## 2. Сквозная архитектура

Полная принятая цепочка:

```text
Physical Fn+1
    ↓
ASUS firmware event 0x61
    ↓
asus-wmi
    ↓
KEY_SWITCHVIDEOMODE
    ↓
XF86Display
    ↓
Niri binding
    ↓
user-status-led cycle
    ↓
persisted mode
   auto | busy | off
    ↓
systemctl --user restart user-status-led.service
    ↓
user-status-led daemon
    ↓
mode evaluation
    ↓
/sys/class/leds/:status/brightness
    ↓
asus-wmi
    ↓
ASUS WMI DEVS 0x00040019
    ↓
physical User-status LED
```

От привязки Niri и ниже каждая ступень — результат работы этого
репозитория (пример привязки, CLI, хранимое состояние, перезапуск
сервиса, демон, запись в светодиод); всё выше — существующее поведение
платформы (прошивка, ядро, XKB/Wayland).

Переназначение ввода в ядре не требуется: проверенный путь уже доставляет
Fn+1 в Niri как `XF86Display` с корректными событиями нажатия и
отпускания, поэтому изменения клавиш на стороне ядра не нужны.

## 3. Модель режимов

- Режимы: `auto`, `busy`, `off`.
- Режим по умолчанию: `auto`.
- Порядок цикла: `auto -> busy -> off -> auto`.

Семантика:

- `busy` — светодиод принудительно включён;
- `off` — светодиод принудительно выключен;
- `auto` — светодиод следует за состоянием сеанса микрофона, полученным из
  топологии PipeWire (раздел 6).

## 4. Хранение состояния

Выбранный режим хранится в XDG state:

```text
${XDG_STATE_HOME:-~/.local/state}/user-status-led/mode
```

Отсутствие состояния означает `auto`.

Принятая поверхность CLI (реализована в v0):

- `user-status-led status`
- `user-status-led set auto`
- `user-status-led set busy`
- `user-status-led set off`
- `user-status-led cycle`

## 5. Путь управления от CLI к демону

Файл сохранённого режима — источник истины. Изменения режима достигают
демона через перезапуск пользовательского сервиса systemd, а не через
активный канал управления:

```text
user-status-led set/cycle
    ↓
atomically persist selected mode
    ↓
systemctl --user restart user-status-led.service
    ↓
new daemon instance reads persisted mode
    ↓
evaluate/apply LED state immediately
    ↓
enter PipeWire monitor loop if needed
```

Принятое поведение:

- `user-status-led set <mode>` и `user-status-led cycle`:
  1. определяют новый режим;
  2. атомарно сохраняют его;
  3. выполняют `systemctl --user restart user-status-led.service`;
  4. завершаются с ненулевым кодом, если перезапуск не удался.
- Сохранённый режим не откатывается при неудачном перезапуске: запрошенное
  состояние остаётся авторитетным и применяется при следующем успешном
  запуске сервиса.
- `user-status-led status` только читает и сообщает сохранённый режим;
  сервис он не перезапускает.
- При запуске демон читает сохранённый режим, немедленно вычисляет и
  применяет требуемое состояние светодиода и только затем входит в обычный
  цикл наблюдения за событиями PipeWire.

Перезапуск выбран вместо DBus, собственного IPC на сокетах, polling или
механизма signal/reload осознанно: это простейший детерминированный
вариант для v0, использующий существующий жизненный цикл
пользовательского сервиса systemd.

Возможное краткое выключение светодиода во время перезапуска — пункт
приёмки для проверки на реальном оборудовании, а не заранее предполагаемая
проблема. Механизм signal/reload не вводится, пока приёмка не покажет
конкретную проблему, например заметное видимое мерцание.

## 6. Семантика AUTO

Принятый концептуальный предикат:

AUTO равен ON, когда существует активный потребитель микрофона — активное
соединение PipeWire от реального `Audio/Source` к работающему клиенту
`Stream/Input/Audio`. AUTO равен OFF, когда такого потребителя микрофона
нет.

```text
Audio/Source
    ↓ active PipeWire link
Stream/Input/Audio (running)
    ↓
AUTO = ON
```

Семантика приглушения на уровне приложения:

- Реальный голосовой звонок Vesktop сохраняет граф микрофона, пока
  микрофон приглушён внутри приложения.
- Поэтому `auto` остаётся ON, пока этот сеанс захвата микрофона активен.
- Завершение звонка удаляет узел захвата микрофона и его связи, и AUTO
  становится OFF.

Светодиод — индикатор статуса сеанса, а не аппаратный индикатор
приглушения микрофона: приглушение внутри приложения не гасит его, пока
сеанс захвата продолжается.

## 7. Отклонённые предикаты AUTO

Следующие предикаты явно отклонены:

- Любой работающий узел `Stream/Input/Audio`. Отклонён, потому что монитор
  sink может владеть работающим потоком захвата и дать ложное
  срабатывание.
- Любой узел `media.category=Capture`. Отклонён по той же причине.
- Сопоставление по именам приложений (Vesktop, Telegram, Firefox,
  Zoom, ...). Отклонено: предикат AUTO определяется топологией графа, а не
  принадлежностью к приложению.
- Жёстко прописанные имена узлов микрофона. Отклонено: предикат нацелен на
  любой реальный `Audio/Source`, а не на конкретное имя узла.

Проверенный пример ложного срабатывания — путь захвата Noctalia Spectrum:

```text
Audio/Sink monitor
    ↓
Noctalia Stream/Input/Audio
```

Это путь захвата от монитора sink, и он НЕ должен включать AUTO — именно
поэтому предикат требует реальный `Audio/Source` как начало связи.

`Audio/Source/Virtual` сейчас вне принятого предиката AUTO, поскольку
подтверждённой потребности в нём нет.

## 8. Модель наблюдения за PipeWire

```text
pw-dump --monitor
    ↓
filter relevant Node/Link event
    ↓
plain pw-dump
    ↓
authoritative complete graph snapshot
    ↓
evaluate AUTO
```

Проверенное поведение `pw-dump --monitor`:

- сразу выдаёт начальное полное состояние одним полным JSON-массивом;
- последующие изменения графа приходят отдельными JSON-массивами;
- удаления выглядят как объекты вида:

```json
{
  "id": 144,
  "info": null
}
```

Принятый дизайн:

- НЕ поддерживать собственный инкрементальный кэш графа PipeWire;
- НЕ использовать периодический опрос (polling);
- НЕ использовать прямые Python-привязки PipeWire в v0;
- использовать monitor только как источник пробуждения для пересчёта;
- использовать свежий снимок обычного `pw-dump` как источник истины;
- игнорировать события монитора, которые не могут повлиять на AUTO.

Фильтрация событий. Снимок выполняется только для события, содержащего
типизированный объект `PipeWire:Interface:Node` или
`PipeWire:Interface:Link`, либо для нетипизированного удаления
(`{ "id": N, "info": null }`), где `N` входит в набор ID узлов/связей из
последнего снимка. Произвольные события монитора не должны запускать
снимки: сам `pw-dump` является клиентом PipeWire, поэтому каждый снимок
порождает события добавления/удаления Client, и реакция на них создаёт
самоиндуцированный цикл «монитор/снимок». Это не гипотеза: первая
приёмка на оборудовании зафиксировала примерно 67% CPU демона в режиме
`auto` именно из-за этого цикла. Хранимый набор ID узлов/связей —
единственное состояние, переносимое между снимками: он существует только
для классификации нетипизированных удалений и полностью заменяется после
каждого свежего снимка; инкрементальным кэшем топологии он не является.

Это осознанный компромисс: небольшой объём дополнительной работы процесса
при относительно редких изменениях графа в обмен на существенно более
простую корректность. Полный повторный дамп после каждого релевантного
пробуждения не может разойтись с фактическим состоянием PipeWire, в
отличие от инкрементального кэша.

## 9. Граница привилегий

Атрибут светодиода:

```text
/sys/class/leds/:status/brightness
```

Принятая модель прав:

```text
root:user-status-led
0660
```

Выделенная группа:

```text
user-status-led
```

Проверенная топология udev.

Устройство:

```text
SUBSYSTEM=="leds"
KERNEL==":status"
```

Родитель:

```text
KERNELS=="asus-nb-wmi"
SUBSYSTEMS=="platform"
DRIVERS=="asus-nb-wmi"
```

Почему такая модель:

- демон остаётся непривилегированным;
- без root-демона;
- без sudo/doas на каждую запись в светодиод;
- без polkit-хелпера;
- без расширенных прав на посторонние светодиоды.

Непривилегированное включение/выключение светодиода и сохранение прав
после перезагрузки уже проверены на оборудовании.

## 10. Модель процессов

Модель процессов (реализована в v0):

- один исполняемый файл только на стандартной библиотеке Python 3;
- один и тот же исполняемый файл предоставляет CLI и поведение демона;
- один пользовательский сервис systemd;
- без собственного API на Unix-сокетах;
- без DBus API;
- без root-сервиса;
- без внутреннего супервизора — жизненным циклом сервиса управляет
  systemd.

Демон избегает избыточных записей яркости: запись выполняется только когда
желаемое физическое состояние светодиода отличается от последнего
применённого.

Чистое завершение: демон по возможности (best effort) выключает светодиод
при чистой остановке, чтобы устаревшее состояние не оставалось намеренно.

## 11. Интеграция с Niri

Проверенный путь ввода:

```text
Fn+1
→ firmware event 0x61
→ KEY_SWITCHVIDEOMODE
→ XF86Display
→ Niri
```

`XF86Display` не имела конфликтующей привязки в активной конфигурации
Niri, и привязка из этого репозитория теперь установлена там.

Принятая привязка:

```text
XF86Display -> user-status-led cycle
```

Пример фрагмента находится в `niri/user-status-led.kdl` — он вставляется
в существующую секцию `binds { }`. Проверено на оборудовании: одно
нажатие даёт одно переключение режима (`auto -> busy -> off -> auto`;
поведение `repeat=false` принято), сервис остаётся активным, а возврат в
`auto` во время активного звонка немедленно пересчитывает состояние
PipeWire и включает светодиод.

## 12. Границы компонентов

Ядро / прошивка:

- предоставляют аппаратный примитив (LED class device, событие клавиши);
- внешние по отношению к этому репозиторию.

udev:

- узкая настройка прав для единственного атрибута светодиода.

Niri:

- превращает существующий ввод пользователя `XF86Display` в вызов CLI.

CLI:

- изменяет и запрашивает выбранный режим.

Демон:

- вычисляет режим и состояние PipeWire;
- записывает желаемое состояние светодиода.

PipeWire:

- предоставляет топологию, управляющую режимом `auto`.

## 13. Вне целей проекта

- Разработка патча ядра.
- Изменения прошивки.
- Переназначение клавиш в ядре.
- Интеграции под конкретные приложения.
- Универсальное определение конференций вне связи с топологией микрофона.
- DBus или собственный IPC.
- Root-демон.
- Собственный синхронизатор графа PipeWire.
- Лишние фреймворки.

## 14. Текущий статус реализации

Архитектура и дизайн приняты. Пользовательская реализация v0 существует:
исполняемый файл `user-status-led` (CLI и демон, только стандартная
библиотека Python 3), `systemd/user-status-led.service`,
`udev/70-asus-user-status-led.rules` и `niri/user-status-led.kdl`.

Приёмка на ASUS ExpertBook B5402CBA пройдена для:

- ручных режимов: управление светодиодом в `busy`/`off`, сохранение
  режима, права, работа сервиса;
- режима `auto` в простое: без цикла загрузки CPU — один долгоживущий
  `pw-dump --monitor`, без порождения обычных `pw-dump`, низкая
  нагрузка на CPU демона (исправление цикла обратной связи проверено на
  оборудовании);
- управляемого захвата реальным микрофоном (`pw-record`): светодиод ON
  во время записи, OFF после остановки;
- отсечения ложных срабатываний: Noctalia Spectrum (захват от монитора
  sink) держит светодиод выключенным;
- реального звонка Vesktop: светодиод ON во время звонка, ON при
  приглушении внутри приложения, OFF после выхода (после короткой
  нормальной очистки графа PipeWire);
- сквозной интеграции Fn+1: `XF86Display` -> `user-status-led cycle` ->
  атомарное сохранение -> перезапуск сервиса -> корректное состояние
  светодиода, одно переключение на нажатие.

Оставшийся объём приёмки:

```text
restart-flicker visual acceptance
reboot/login lifecycle
```

Перезапуск через `set`/`cycle` функционально работает; явной визуальной
оценки мерцания при перезапуске пока не проводилось. Жизненный цикл
перезагрузки/входа в систему (сохранение режима, запуск сервиса после
входа, права udev, старт AUTO, переключение Fn+1) не проверен.
